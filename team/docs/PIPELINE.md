# 候補準備と計測を重ねる

Discord上の各主Agentが、優先順位・結果の解釈・他メンバーとの調整を持つ。
利用中のClaude/CodexにnativeなSubAgent機能があれば、独立した仕事を委譲する。
役割と数はタスクごとに変え、選手3人をAgent数の上限にしない。
機能がなければ主Agentが同じ完了条件まで自走する。別セッションの自動起動や
Discord Botの実装済みを前提にしない。本番のメンバー間連携は[Discord](DISCORD.md)。

## 小さく流す

開始時の目安は主Agentごとに「実装中1件＋次候補の調査1件」。
調査で根拠・仕様・失敗条件が揃ってから実装へ進む。小さな修正に委譲・独立レビューを
必須化せず、作業の独立性と期待する時間短縮がある場合に使う。

| 担当 | 完了まで持つ仕事 |
|---|---|
| 主Agent | 仮説の選択、共有台帳の担当、依存・競合調整、Discord窓口、結果の解釈 |
| 実装担当 | 独立worktreeで実装、関連QA、commit、他者が使えるREADY資料まで |
| 調査担当 | 次候補の採点経路・仕様・過去の失敗・テスト観点。必要な変更の独立レビュー |
| 単一の公式統合担当 | 現stableへの合成、必要な再検証、公式計測、採否または復旧 |

実装担当は主AgentでもSubAgentでもよい。調査担当を同じ候補のレビューへ移すなど、
役割は動的にする。同一候補のwriterは1人、可変worktreeも1担当に限る。
読み取り調査、テスト設計、別候補の準備は重ねられるが、同じ作業ツリーのHEADを
テスト中に動かさない。共有DB・設定を変える検証には対象環境の占有が必要。

例: Aの実装中にBを調査し、Aの関連検証中にBを実装できるか判断する。
Aの公式ベンチ中はBの準備を続ける。A採用で前提が変わればBを再確認する。
依存した候補を先回りして実装し、後で合成し直す費用も見積もる。
各環境のdeploy/bench排他と公式統合の単一ownerは維持する。

共有READYが既定2件以上なら、自動claimの既存backpressureに従い、
追加実装より既存候補の調査・比較・品質修正へ向かう。明示claimは既存の例外であり、
queueと残り時間を見た理由を残す。Agentを増やして未検証コードを積まない。
統合担当はREADYの有無を作業境界で確認し、現在の得点見込み・依存・総費用から
次を選ぶ。主Agentからの改めての「次へ」の指示待ちを工程に組み込まない。
統合担当にも「合成→actual SHAの関連QA→次の計測または復旧」を完了単位として渡す。
合成だけを返して親が検証を開始するまで待たず、同じ委譲の中で続ける。
処理中の主Agentは、独立した調査やプラグイン整備を行える。対象環境の操作は引き続き
その予約ownerだけが行い、次の権限や条件が未充足なら実際の待ち理由を残す。

## 委譲時に渡す契約

候補票または依頼に以下を短く揃える。別の設計会議・承認ゲートは作らない。

- タスクID、base SHA、原因仮説、採点とのつながり、根拠artifact・仕様参照。
- 単一writer、worktree、編集範囲、依存・競合、実行してよい検証と操作範囲。
- 完了条件: commit済みsource、関連QAの実行結果、候補票、共有できる根拠、READY。
- 時間上限と次に報告する境界。自力で修正してよい範囲、打ち切り条件、失敗時の
  証拠保存・品質保留・復旧先。目的や権限を越える選択は主Agentへ戻す。
- 調査担当には、結論・棄却理由・最小の識別観測・テスト観点を成果とし、
  実装担当の可変worktreeを変更しないことを伝える。

実装担当は実装だけ返さず、[prepare-candidate](../../skills/prepare-candidate/SKILL.md)
で関連検証・commit・READYまで完結する。主Agentがexact task IDと許可する
`task-stage` / `task-ready`コマンドを明示委譲し、同じ人間開始主セッション内の
native SubAgentが既存の同一認証文脈・接続方式を使える場合、親SESSION principalで
そのタスクを提出してよい。ownerとDiscord窓口は主Agentに残し、内部worker IDを
reason/evidenceへ記録する。別メンバー・独立joinとは扱わない。

これは既存ownerの責任下での準備委譲であり、認証guardの変更・回避や追加CLIを
意味しない。別セッション・他人のidentityを借用せず、credentialやreservation tokenを
新たに共有しない。env取得・deploy・bench・採否の権限を暗黙に委譲しない。
source-bound QA・commit・READY条件も変わらない。
接続手段が使えない場合のみ、task ID、source/base SHA、変更パス、実チェックの結果・
証拠・時間、リスク・推奨を短い機械可読completion packageで親へ返す。
親はまとめて台帳へ提出し、工程ごとの再許可待ちや同じ調査のやり直しを挟まない。

## 品質と履歴を省略しない

テスト観点・fixture設計は実装と重ねる。PASSの証拠は実行したsource SHAへ結び付ける。
統合で関連するsourceが変わったら実際の統合SHAを検証する。変更のない範囲の証拠は
scope・条件を確認して再利用する。[検証方針](VALIDATION.md)に沿って既存テスト・
formatter/Lint一式の実行を基本とし、実測で重い検査だけ範囲・頻度・並列実行を調整する。
cold/warm・build重複・秒数と、省略した範囲・理由を残す。
新coverageや全ケースのLLM契約レビューをREADYの既定条件にしない。具体的な疑義に対する
準備レビューは共有targetの占有外で行い、実ベンチを性能とcheckerの正しさの共通判断に使う。
省略範囲を記録し、既知の欠陥・未解消holdはベンチPASSでも免除しない。
最終版の必要な確認は時間予算へ含める。

品質保留は元SHA・失敗・分類・修正を結び付ける。[品質保留](PARALLEL_QUALITY.md)の
既存手順を使い、後のcleanな計測・最終2走・別タスクへの付け替えで未解消の保留を
免除しない。入力衝突なら仕様上の期待と再現条件を確認して修正する。
失敗を隠すためにベンチ入力を都合よく書き換えたり、再試行して失敗を捨てたり、
assertionや仕様を緩めたりしない。仕様を守るunique ID生成など、原因を修復する
正当な衝突対策は関連する再現検証を伴って進める。

正しさは通ったが効果未確認の案は、prior recordと当時のbase・負荷・機構・結果を残す。
再検討には変わった負荷、別機構、識別できる新しい根拠を示す。同じSHA・同じ条件で
良い得点を引くまで回すことや、実質同じtreeのcommitを作り直すことはしない。
問題固有のSQL・施策は練習のknowledgeへ保存し、汎用Skillへ固定レシピとして入れない。
人間判断、採点条件、復旧の条件は[POLICY](../POLICY.md)と既存実験手順に従う。

## 残り時間と流れを測る

候補の費用は「検討→実装→検証→handoff/queue→deploy→比較→修正・復旧」全体と、
最終確認・cleanupまで含める。Agentの作業時間の合計と競技のwall clockは分ける。
開始時に上限を置き、重要な失敗・前提変更・上限到達時に更新する。
予め置いたsource固定時刻は目安であり、必要な最終確認・復旧・cleanupを残して有用な
候補が収まるなら続ける。人間の明示freeze・停止指示と実際の終了時刻は守る。

調査開始、実装開始、検証開始、handoffを既存の作業境界で記録する。テスト設計は
調査中にも起こるため、工程ラベルだけで純粋な思考・編集時間だと断定しない。
進捗記録のために工程を止めたり、各stageの承認待ちを追加したりしない。
CLAIMEDタスクの現在ownerは、任意の観測として以下を使える。

```bash
python3 "$K/scripts/team/control.py" task-stage --id T-0001 --agent SESSION \
  --phase implementation --reason '根拠確認を終え、独立worktreeで実装開始'
python3 "$K/scripts/team/control.py" task-stage --id T-0001 --agent SESSION \
  --phase validation --sha FULL40 --evidence CHECK_RECORD --reason '対象sourceの関連検証開始'
python3 "$K/scripts/team/control.py" pipeline-status --agent SESSION
```

phaseは`analysis|implementation|validation|handoff`。stageはappend-onlyの観測であり、
品質証明・担当変更・READYの代わりにはならない。validationのSHAと提出SHAが違う場合、
そのstageを提出sourceの検証済み根拠にしない。成果は既存のREADY等へ記録する。
`pipeline-status`は読み取り専用で、未記録の工程を推定して埋めない。
見る指標は次の通り。

- READY提出から統合開始までの待ち時間と理由（合成、占有、優先順位、共有待ち等）。
- 計測可能な環境が空いた時間、READYが無かった時間、準備・final・cleanup等の理由。
- 検討・実装・検証の区間、実テスト時間、引渡し時間、重なった区間と未記録区間。
- 合成完了からactual SHAの関連QA開始までの間隔。READY提出前の引渡しも記録する。
- 最終有効スコア、候補全体の所要時間、品質保留の修正・回収、効果未確認の理由。

現台帳には厳密な統合開始markerが無いため、READY→実統合開始の待ち時間はunknown。
提出からの経過時間をそのままqueue待ち時間と呼ばない。必要な境界が実測できた場合に
上記の待ちを求める。区間が重なる値を足して全体時間にしない。
未記録時間を待ち時間と推測せず、短縮率や
得点への因果効果は[同条件の比較](COMPARISON.md)がある場合にだけ述べる。
