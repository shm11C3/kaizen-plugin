# Discordで連携する

各メンバーが自分のPCでClaude/Codexを起動し、非公開のチームDiscordで
議論・発見・作業調整を共有する。各セッションは自身で共有情報を読み、作業を選ぶ。
参加時の指示や他セッションの会話履歴が自動共有されるとは扱わない。
本番手順は独立セッション同士の連携を前提とする。
各主セッション内では、利用可能なnative SubAgentで候補準備と次候補調査を重ねてよい。
主Agentが共有台帳の担当・Discord窓口を持ち、内部の分担は他メンバーの会話確認を
代替しない。分担・完了契約・backpressureは[PIPELINE](PIPELINE.md)を参照する。

## 共有する情報

| 場所 | 内容 |
|---|---|
| `#ops` | 参加、占有・障害、担当交代、停止・freeze |
| `#discoveries` | 観測根拠、原因仮説、関連タスク |
| `#tasks`の各スレッド | タスクID、担当セッション、進捗・依存、候補・修正のSHA |
| `#benchmarks` | 環境、実験ID、統合SHA、条件、結果、品質保留と再計測 |
| `#decisions` | 人間の方針、具体的な採否・リスク判断、対象SHA・操作範囲 |

Discordは会話と判断への参照先、共通ホストの台帳はタスク担当・占有の正本、
Gitは変更、kaizen記録は実測と採否の根拠として使う。Discordへの担当宣言だけでは
取得・占有は成立しない。台帳が変わったときは関連スレッドにも状態を伝える。

### 会話媒体を選び直す

Discordは現在の既定であり、媒体の維持自体を目的にしない。既存の利用許可・当日規約の
範囲でGitHub Issue/PR等の方が有効なら、AIは切替を判断してよい。読み落とし、応答・
引渡しの待ち、API消費、同期実装と移行の費用を比べ、移行先と未完了の議論への参照を
共有する。会話媒体を変えても担当・占有は共有台帳、実測・採否はkaizen記録を正本とし、
Issue AssigneeやPR mergeを取得・採用の代用にしない。追加の権限が必要な操作は
[POLICY](../POLICY.md)の既存境界で扱う。

## 参加時

1. チームのサーバーとチャンネルID、各自が使うMCP/Bot等の接続手段を確認する。
   IDは環境のhost-configの`discord`ブロック（`guild_id`と5チャンネルのsnowflake）に
   置き、`join.py --env NAME`の出力で受け取る。MCPはBotの所属サーバー一覧や
   チャンネル名検索を持たないため、IDを知らないセッションは何も読めない。
   練習・検証では、その環境のブロックに書いたチャンネルだけを使う。名前が似た
   旧チャンネルや本番用チャンネルへ投稿しない。使わなくなったチャンネルには
   トピックか最後の投稿で「使用終了・移動先」を残す。
   GitHubユーザー名とDiscord表示名の対応をチーム内で共有する。
2. `discord`ブロックの全チャンネルの新着をまとめて読む（`#ops`だけで判断しない）。
   現在の`#decisions`と関連するタスクの議論も読む。
   現在の方針・残り時間・停止指示・担当を把握し、`control.py queue`と照合する。
3. 自分の接続で必要な履歴を読めることと、許可されたチャンネルに投稿できることを
   確認する。過去のローカル検証は実Discord接続の確認を代替しない。
4. GitHubユーザー名、セッションID、provider、実際に読み込んだplugin版、担当可能な
   環境を`#ops`へ共有する。タスク担当は動的に選び、固定のDB/API担当にしない。

`join.py`の`joined: true`はモデル・Git・SSM・plugin版の確認結果で、Discord疎通は
含まない。使用する接続はチームで設定する。このplugin自体はDiscord Botや
新着でのAI起動を実装していない。

## 共有Botで投稿するとき

複数のセッションが同じBotで投稿すると、作者は全員同じBot名になる。すべての投稿を
`[セッションID]`で始める（例: `[shm11C3-claude-01] T-0002 READY 0fe93ff`）。
読む側は作者ではなくこの接頭辞で発言者と担当を判断し、接頭辞のない投稿は
発言者不明として扱う。人間の投稿は各自のアカウントなので接頭辞は不要。

新着の通知はないため、他のセッションの返答を待つ間は作業の区切りごとに読み直す。
最後に読んだ位置は、チャンネルごとに`<channel>: <message-id> <JST時刻>`の形で
自分の作業メモへ残す。未読追跡のあるMCP（readerIdごとの`read_unread`/`ack_unread`）
なら、セッションIDをreaderIdにしてページ全体を読んでからackする。
結果が空でも、返ったreceiptは毎回ackする。ackしない間は同じsnapshotが返り続け、
新着が届いていても「空」に見える（R3で他Agentの指摘を約3分見落とした）。

## 作業の区切りで読む・伝える

- 取得前: 最新の方針、関連スレッド、発見、台帳を読む。原子的な`task-claim`に
  成功してから、タスクIDと実際のセッションIDでCLAIMを伝える。
- 提出時: GitHubユーザー名・セッション、branch/source SHA、base、根拠、検証、
  影響範囲を候補票にまとめる。他のPCが読めるartifactの参照先を付ける。
  主Agentは内部の実装・調査担当から結果を集め、候補単位で共有する。
  工程ごとの開始許可をDiscordで待たず、合意した範囲はREADYまで進める。
- 統合・計測時: 統合担当は占有を取り、対象環境と候補SHAを`#ops`へ通知する。
  計測結果と採否は実験記録・台帳へ反映してから共有する。
- 品質保留時: 元候補・失敗根拠・分類・次の調査を同じスレッドへ追記する。
  修正版と再計測は元の保留へつなぐ。提出だけで解消と通知しない。
- 人間判断時: 選択肢・根拠・推奨・対象SHA/操作範囲を揃えて`#decisions`へ渡す。
  実際の人間の回答メッセージへの参照を採否記録へ残す。
- 再開・交代時: 未読、方針変更、台帳、Git、実験記録を読み直す。長い作業の途中も
  安全な区切りで停止・freeze等を確認する。

作業中は約1分を目安に新着を確認し、停止・方針変更・依存解除には速く応答する。
長い処理で主Agentの確認が途切れる場合、利用可能なnative SubAgentに巡回を委譲してよい。
巡回担当は読み取りと新着本文・参照先の通知に限定し、担当取得、候補の採否、環境操作や
外部への返信を暗黙に代行しない。主Agentが原文と正本を確認して判断する。
履歴adapterがreader ID・ページ確認・ACKを提供する場合は読み取り担当ごとに保持し、
未読や切れた出力を確認済みにしない。新着がないときの定型投稿や重複する全履歴取得は避け、
既読位置から読む。

読み取り位置はセッションごとに記録する。最後に確認したメッセージID・関連スレッド
へのリンク・取得日時を引き継ぐが、他のセッションが読んだことを自分の確認にしない。
手元の絶対パスしかない証拠は共通ホストのartifact等へ置き、参照先を共有する。

送信は接続の成功結果を確認してから送信済みと扱う。結果不明なら投稿履歴を確認し、
同じ内容を盲目的に再送しない。資格情報や巨大な生ログは投稿しない。
接続障害時は台帳とartifactを保持し、再送・共有が必要な内容を記録する。
人間が明示的に中継する場合は投稿用文章と参照先を渡し、受信確認を揃える。

MCPで履歴を読めることと、新着でセッションが自動起動することは別である。
現行は起動済みのセッションまたは委譲した巡回担当が確認する。イベント駆動を追加する場合は
別途Botと起動側を接続して検証し、未実装の自動wakeを前提に進めない。

## GitHubユーザー名とセッションID

- 実装ブランチ: `<github-login>/T-0001-query-index`
- 統合・計測ブランチ: `<github-login>/exp/001-query-index`
- plugin改善ブランチ: `<github-login>/tooling/<task-or-topic>`
- セッションID: `<github-login>-codex-01`、`<github-login>-claude-01`等。
  同じ人の並列セッションでもIDを分ける。役割とGitHubユーザー名は固定で結び付けない。

各自のGitHubユーザー名を使い、リポジトリ所有者やGitの`user.name`から推測しない。
GitHub CLIを利用する場合は`gh api user --jq .login`で確認できる。
命名は担当を読み取る規約であり、GitHubの認可や台帳の原子的な取得を置き換えない。
交代しても既存候補のbranch/SHAは参照を維持し、履歴を書き換えて改名しない。
新しい修正ブランチを作る場合は後任のGitHubユーザー名にし、元候補をリンクする。
既存のセッションIDも稼働中に改名せず、担当交代は台帳のhandoffで行う。
