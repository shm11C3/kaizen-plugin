# 規約・手動操作・並列検証への適応

確認日: 2026-10-18 JST。過去大会を運用設計の材料とし、当日のマニュアル・
ポータルの指示を優先する。以下の設計判断と公式資料の事実を区別する。

## 公式資料で確認できる違い

| 資料 | 確認した条件 | 運用への反映 |
|---|---|---|
| [ISUCON12予選規定](https://isucon.net/archives/56671734.html) | 外部資源は開発・テスト用途と競技ベンチ中の処理委譲で扱いが異なる。再起動順は保証されない | 外部検証環境の結果と公式結果を区別し、複数ホストの再起動依存を確認する |
| [ISUCON13当日マニュアル](https://github.com/isucon/isucon13/blob/main/docs/cautionary_note.md) | ポータルがWAITING/RUNNING中は次を投入できない。複数スタックは可能だが、終了時の登録環境混在は失格 | ポータル待ちを占有期間に含め、検証用と公式登録環境を区別する |
| [ISUCON14当日マニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md) | 最後の負荷走行が最終スコア。再起動、同一VPC、性能再現、計測後のデータ永続性と画面を確認する | 最高値だけを残さず、最後の成功と配備版を揃える。起動確認だけを追試適合と呼ばない |
| [ISUCON2026規定](https://isucon.net/archives/59966826.html) | AI利用、外部の開発・テストは許可。競技ベンチ中の外部委譲は禁止。当日マニュアルが優先 | AI自走と公式環境の資源境界を別々に設定し、当日資料で再確認する |

管理画面による操作手順が記載されているだけで、全API自動化が禁止と断言しない。
逆に非公開APIやベンチマーカーへのログインを利用できると推測しない。
権限・方法が不明な操作だけを要確認にし、独立した実装・調査は進める。

## 操作ごとに方法を決める

当日、共有のRULESとセッション記録へ、根拠URL/節・確認日時・対象環境・
操作方法を残す。分類は`auto`、`operator`、`forbidden`、`unconfirmed`。
環境構築、接続、デプロイ、公式ベンチ、結果取得、登録環境確認、問い合わせ、
再起動、永続性・画面確認を個別に決める。これは手順上の分類であり、
すべてを新たな機械的ガードが強制する実装ではない。

`operator`ではAIが対象、SHA、操作内容、期待結果、結果の戻し方を準備し、
人間が指定された操作を行う。完了待ちを失敗扱いせず、確認結果から再開する。
必要な画面操作の依頼は、改善の採否承認とは別である。

既存の`BENCH_MODE=manual`を使う場合:

1. 統合担当が環境を占有し、`target ... bench LABEL --reserve`で物理枠を確保する。
2. 人間が正しい公式対象を選び、ポータルから開始する。ジョブ識別子と生結果を保存する。
3. WAITING/RUNNINGを通じて占有を維持し、deployや観測設定を変更しない。
4. 終了と配備版を確認し、`--result`で実際のpass/score/errorsを記録する。
   不明なerrorsやrequestsを0にしない。`--requests`は同じ対象を数えた実データのみ。
5. 結果不明時は状態を調べ、終了確認後のみ`--abandon`する。時間だけで解放しない。

## 並列検証の構成

公式環境は従来どおり直列にする。独立したsandboxごとに実装候補を検証し、
有望な候補を現在の公式stableへ統合して公式環境で確認する。
sandboxのスコアを公式スコアや自動採用の根拠に置き換えない。

各sandboxはアプリ、DB/初期データ、決済等のモック、計測機、ログ、設定、
作業clone、実験状態、占有を分離する。タスク台帳だけは共通にする。同じアプリDBや負荷生成CPUを共有した計測を
独立比較と扱わない。各レーンで同じ基準版と候補を測り、環境差を記録する。
公式稼働系からsandboxへ処理が流れないネットワーク境界を設ける。

`control.py --host-config`には既存の`state_db`と`target_config`を**対で**指定できる。
同じstate_dbとレーン別target_config・environmentを指定する。
レーン別設定・project・knowledge・host群を用意し、実対象の重複がないことを
確認する。設定ファイル名が違うだけでは資源分離の証明にならない。
公式登録されるテンプレートやenvcheckを複製する場合は、登録先への副作用を
確認する。一般sandboxが許可されることと、公式スタック追加の条件は別である。

共通タスク台帳と環境別ロックの登録・使用手順は
[並列検証と品質保留](PARALLEL_QUALITY.md)を参照する。
sandbox自動作成・複数レーン配備の実機検証は未実施。まず2レーン程度で、構築・同期・再現・公式での再確認に
使う時間より待ち時間削減が大きいか測る。規約根拠・分離・停止手順が揃うまで
本番用環境へ追加サーバーを接続しない。
