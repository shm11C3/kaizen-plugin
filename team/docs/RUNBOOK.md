# 当日の手順

この文書とコマンドはプラグイン側にあります。`K` はインストール済みkaizenのルートです。競技用cloneへ管理スクリプトをコピーしません。

## 事前準備

- 3人がPrivateリポジトリをcloneでき、各自のAWS認証で共通ホストへ接続できる。
- 各人の実PCで同じreleaseのjoinを通す。Claude/Codexの実モデル疎通まで確認し、cacheや他人の認証で代用しない。
- [Discord連携手順](DISCORD.md)で非公開サーバーの読取・投稿、現在の方針確認、GitHubユーザー名とセッションIDの対応を各人の接続で確認する。
- 過去問でタスク同時取得、候補統合、計測、採用、復旧、接続切断、担当交代を試す。
- 競技の当日ルールでAI・外部サービス・追加ホスト・問題情報の取り扱いを確認する。
- 終了時刻・新規変更停止時刻・最終ベンチの時間枠を人間が決める。
- 現在は競技用ホスト・ソース・ベンチは空。練習用サーバーを自動で競技対象にしない。

## 開始

1. 最初の統合担当を決める。共通ホストの占有・実行中処理・ディスク容量を確認する。
2. 当日公開されたアプリ・配備対象設定を、問題の構成に合わせて取り込む。秘密鍵・認証情報・巨大データを除き、初期コードをmainにcommitしてpushする。
3. kaizenのsetupで当日マニュアルに基づくpreset、`.kaizen/config.sh`、`.kaizen/RULES.md`を作る。対象ホスト・配備範囲・初期化・build・health・bench方式を明示する。
4. setupの初回配備・資源初期化・stable capture・復旧ドリルは、環境占有を保持して指定した統合担当がkaizenのsetup手順と[RECOVERY](RECOVERY.md)を実行する。通常ラッパーを有効にする前の明示的な初期化手順とする。
5. 初期ベンチの正しさ・スコア・SHA・条件を取得する。復旧手順を実際に試し、stableを確認する。
6. `/srv/isucon/state/target.json`を設定例から作り、rulesと復旧確認をtrueにする。ラッパー経由でstatusとverifyを確認する。
7. 観測資料を共有ホストへ保存する。各AIを起動し、戦略・残り時間・自走範囲を伝える。

## 改善ループ

1. Discordの最新方針・関連スレッドと台帳を確認し、[戦略手順](STRATEGY.md)で採点への影響・総所要時間・反証条件を揃え、AIが根拠付きタスクを作成・取得し、独立ブランチで実装・検証する。
2. 候補と検証を台帳へ提出し、Discordの関連スレッドにbranch/SHA・根拠を共有して、他のタスクへ進む。
3. 統合担当は効果見込み・計測時間・リスク・依存関係で候補を選ぶ。完成順に固定しない。
4. 現在のstableへ取り込み、1候補ずつデプロイ・計測・評価する。
5. 通常改善は採用、正しさ違反は復旧、計測・調査不足はNEEDS_MEASUREMENT。価値・リスクの具体的な選択をNEEDS_HUMANへ渡す。結果を記録して共有する。
6. 採用で前提が変わったタスクを再確認する。予測が外れたとき・strategy通知が出たときは、安定状態で原因仮説と実験順を見直す。
7. READY滞留時はqueueの調査・比較タスクを取得する。新たな計測や設定変更が必要なら統合担当の枠へ載せる。

## 統合担当の交代

採用または復旧済みで、対象操作・ポータルベンチが終了した区切りを使う。`team/templates/HANDOFF.md`を埋め、後任が実状態を確認する。占有を保持したまま、前任が次を実行する。

```bash
python3 "$K/scripts/team/control.py" env-handoff --agent FROM_SESSION --token TOKEN \
  --to TO_SESSION --reason 'stable確認済み、実行中処理なし'
```

後任用の新tokenが返る。古いtokenは無効になる。タスクの担当も移す必要があればtask-handoffで明示する。

## 接続切断・処理中断

1. 占有を消さず、SSMのCommand IDとコマンド結果を確認する。
2. 共通ホストの実行中プロセスとローカルprocess lock、競技サーバー各台の配備SHA・health、ポータルベンチの状態を調べる。
3. 生ログとkaizen状態から、終了済み・継続中・部分配備を区別する。SSHやSSMの切断は処理終了の証拠にならない。
4. 継続中なら待つ。部分配備や不明状態なら、事実を揃えて復旧する。正体不明のまま再デプロイしない。
5. 記録を確定してから占有を移す／解放する。自動期限切れやforce解除は用意していない。

## 終了前

- 新たな高リスク変更を止め、未採用候補を配備しない。
- 採用済みstable、配備中SHA、GitHubのmainを照合する。
- 資源bundleも照合する。最終復旧・最終ベンチの枠を物理予算へ先に含める。
- サービスの起動・疎通・再起動後の設定保持・ベンチの正しさを確認する。
- スローログ、profiling、debug、一時設定を確認する。観測モードのスコアと通常スコアを混ぜない。
- 再起動試験や最終ベンチは、当日のルールと残り時間に沿って担当AIが実施順を決め、既に許可された操作は自走する。ルールで人手に限定された操作や合意外の選択だけを人間へ渡す。
- 最終結果・設定・未完了タスクを保存し、全AIへ停止を伝える。
- 共通ホストの状態をバックアップする。不要になった共通EC2は明示的に停止する。競技サーバーの終了は競技ルールに従う。
