# プラグインの効果を比較する過去問試験

これは実行前の検証手順であり、kaizenの優位性を示す結果ではない。競技用リポジトリは更新せず、専用の検証用リポジトリと隔離した環境を使う。既存の異なる問題・条件の練習結果を比較群に流用しない。

## まず比べるものを一つに固定する

Aは最小構成（Claude/Codex、短い共通指示、Git、配備・復旧・排他ベンチの共通スクリプト）。Bは同じ構成に固定releaseのkaizenを導入する。両群とも3セッションとし、単体対3体の比較は別の試験にする。安全な測定に必要な共通スクリプトはAにも渡す。Bだけの手動支援で試験を成立させない。

最初の比較はプラグイン全体の効果。Bの版・knowledge snapshot・運用設定を記録する。差があってもstrategy機能単独の効果とは主張しない。個別機能は後で一つずつ有効・無効を変えて比べる。

## 開始前に固定・記録する条件

- 未使用の過去問、同じ初期ソースSHA、データ・schema・設定・初期化手順。既知の解答や他群の成果は渡さない。
- 同じホスト構成・機種・ストレージ・ベンチ、モデルと推論設定、3セッション、利用予算・上限制約、制限時間（例120分）。モデルの実際の設定・起動成功も記録する。
- 同じ問題資料・外部ヒントの許可範囲、人間の初期指示・介入方針と上限、配備・計測・復旧用の共通スクリプトSHA。
- 主要指標は締切時に選択済みの版の、再起動後の正しさと有効スコア。同じ回数の最終サンプル（最低2回）を両群に取る。選択後は修正・再選択せず、再起動確認の手順と時間枠も両群共通にする。
- 補助指標は最初の検証済み改善採用までの時間、人間の介入回数、失敗・復旧による時間消費。最高スコアだけを選ばない。

予算はAPI token上限や実際の契約上の利用制約など測れる形で記録する。token数と実費を混同しない。プロバイダ共通の厳密な上限が使えなければ、その制約と実際の利用量を残す。

## 実行と記録

1. 両群の基準版・資源fingerprint・ベンチ成功を確認する。別環境ならホスト負荷等の条件も記録し、順次実行なら初期状態への完全復旧を確認する。
2. 同じ開始指示で開始する。セットアップ時間の内外を事前に固定し、除外した時間も別記録する。
3. 人間の方向付け・承認・手動修復は時刻と根拠artifactを記録する。通常の起動・停止指示との境界も共通にする。
4. 締切で新たな改善を止め、時間内に選択した版を固定する。実行中処理の終了・復旧は記録し、時間外の改善を加えない。
5. 共通の最終確認を行い、再起動・正しさ・スコア・資源・実行版を照合する。失敗した版に有効スコアを付けない。
6. `team/templates/TRIAL.json`を群ごとに埋めて比較する。kaizen群のrecordやtimelineも根拠に使えるが、Aにも同じ指標を記録する。初回採用は実装開始ではなく、比較で改善と品質を確認して採用した時点。

```bash
python3 "$K/scripts/compare.py" /path/to/minimal-trial.json /path/to/kaizen-trial.json
```

記録フィールドの例（下の数値・参照は形式を示す架空例で、実測ではない）:

```json
{
  "firstVerifiedPromotion": {"at": "2026-10-17T00:10:00Z", "artifact": "artifacts/adoption.json"},
  "finalVerification": {
    "revision": "時間内に選択した実際のSHA",
    "selectedAt": "2026-10-17T01:59:00Z",
    "restartPassed": true,
    "correctnessPassed": true,
    "scores": [100, 110],
    "artifact": "artifacts/final-restart-and-bench.json"
  },
  "humanInterventions": [{"at": "2026-10-17T00:20:00Z", "artifact": "artifacts/human-steering-01.md"}],
  "failureRecoveryIntervals": [{"startedAt": "2026-10-17T00:30:00Z", "endedAt": "2026-10-17T00:35:00Z", "artifact": "artifacts/recovery-01.log"}]
}
```

介入・損失を記録してゼロなら`[]`、未記録ならnull。初回採用なしはnull。最終確認が未実施ならnullとし、失敗した場合はfalseと実際の根拠を残す。

ツールは入力された主要条件の一致と時刻・数値・根拠参照の存在をチェックし、指標を並べる。ホスト、参照先の実在・内容、申告の正しさは検証しない。未記録はnullとし、介入ゼロ・損失ゼロと解釈しない。失敗と復旧の重複区間は一度だけ数える。最終確認の結果は締切時の版に帰属させ、時間内最高値と混ぜない。

## 結果から次を決める

１組の比較は事例。試行順・ホスト差・モデルの確率的な探索・計測ノイズがあるため、反復し、可能なら順序を入れ替える。最終サンプルのばらつきと試行間のばらつきは別に扱う。今回の結果で調整した後は、その同じ試行を未使用の検証データとは呼ばない。

優位性が見えなければ、復旧・待機・調整に使った時間、見込み違い、同じ仮説の反復を確認する。通知やタスク管理を増やす前に、得点へつながらなかった手順を減らす。安全・復旧に必要な共通基盤の価値と、探索を速める機能の効果を区別する。
