# 実験を選び、停滞時に方針を見直す

目的は制限時間内の最終有効スコア。実験数、commit数、AI稼働率だけでは成功としない。人間の戦略・除外事項・終了時刻を守り、通常の調査・実装・検証・採用は自走する。

## 次の実験を決める

統合担当が共有の`.kaizen/plan.md`を持ち、各メンバーはタスク・観測資料を入力する。`knowledge.sh plan`は候補と過去の結果を提示する。過去の採用率を今回の成功確率と解釈せず、次を揃えて順番を決める。

| 項目 | 記録すること |
|---|---|
| 採点とのつながり | 直接効く採点項目とマニュアル参照、または共有CPU・DB・lockなどを介する影響と観測根拠。不明なら短い調査を先に行う |
| 原因の説明 | 処理が重いのか、待ち時間なのか。どの資源が制約で、変更により何が解消するか |
| 効果と不確実性 | スコアへの期待効果と、その説明が成立する条件。局所的な速度改善だけで得点増加を断言しない |
| 総所要時間 | 検討、実装、ビルド・テスト、引渡し・キュー待ち、配備、baseline更新、候補計測、修正・復旧、最終確認・cleanup。並行区間と依存を踏まえ、残り時間に収まるか |
| 前提と競合 | 必要な変更・現stable・触る資源・他候補との依存。採用後に前提が消えないか |
| 反証と打ち切り | どの観測で仮説を捨てるか、何回・何分で止めるか、別の説明と区別できるか |

`hypothesize`に固定の「index→N+1→cache」の順番はない。コーパスにない観測由来の案も追加する。基準版が変わったら保存された計画を読み直す。planの再生成は人間・AIの選択と独自の案を残すが、保存された判断が現在も正しいとは限らない。

Go／Rustの採用も[言語選択の比較軸](RUST_BUILD.md)で判断する。ビルド・テストの速度、
実行性能、コンパイル時の安全性と不具合修正費用を、最終有効スコアと残り時間へ結び付ける。

後続の改善を容易にする構造変更も、解消する具体的な障害、依存候補、削減する修正・検証費用、
残り時間での回収を根拠に優先順位へ入れる。[準備フェーズ](PHASES.md)の既存手順を使い、
今回のスコア差だけで候補から除外しない。準備の成果と得点の実証は区別して記録する。

複数の不可分な編集が一つの機構を実現する場合、組合せ候補として明示的に測る。前提変更だけのスコアが曖昧なら、その後の効果を推測して自動採用しない。品質・比較・得点・変更資源の復旧を実証し、合意した目的と制約を守る改善は構造変更でもAIが採用する。副指標の悪化や複数案の存在だけで人間待ちにせず、合意を超える具体的な選択だけを[POLICY](../POLICY.md#adoption-and-human-judgment)に従って渡す。

## 停滞を検知したら

不採用を一括して「失敗」と数えず、根拠を残す。採用率だけを上げるために
小さな変更を選ばず、最終スコアの増分と総所要時間を確認する。

| 理由 | 次に行うこと |
|---|---|
| 正しさ違反 | 失敗リクエストと期待仕様を特定し、担当者が原因修正・再現検証する |
| warning/timeout・品質不明 | 種類・対象API・分母・基準版の有無を調べる。件数だけでエラー率増加と断定しない |
| 性能が伸びない | 採点への経路、制約資源の移動、ノイズを調べ、継続・別機構・打ち切りを選ぶ |
| 計測条件が不適合 | 変わった資源や観測負荷を特定し、条件を揃えてから再計測する |

品質で保留した改善は、元の候補SHA・失敗の証拠・修正タスク・再試行実験を
関連付ける。別のボトルネックが表面化したなら、修正と不可分な組合せ候補を
現在のstableに対して測る。原因説明が変わらない再実行を続けない。
修正して後続で採用された変更は「回収」と記録し、最初から採用したと書き換えない。

構築・キュー待ち・計測・復旧・原因調査を分けて時間を記録する。
序盤は大きな効果が見込める案を優先し、残り時間と最終確認枠に収まる実験だけを
開始する。サンプルは現在の最小数と品質条件を守り、ばらつきや小差が判断を
変えうる場合に追加する。追加計測を惰性で行わず、情報価値と待ち時間を比較する。
繰り返しの運用作業は[workflow手順](WORKFLOW.md)へ渡す。練習でも汎用Skillは
改善し、問題・環境固有の手順は知見として保存する。本番では固有Skillも作る。

`status.sh`と`experiment.sh record`は履歴に基づくstrategy通知を出す。手動確認は`strategy.sh status`、検討テンプレートは`strategy.sh review`。チームでは統合担当が`control.py target ... strategy status` / `strategy review`を使う。

既定の通知条件は、固定ルールの品質・性能比較に合格しない通常計測が3件続く、またはその実験内の経過時間が累計30分に達すること。比較の合格と実際の採用は別に集計する。通常候補sampleがあり、品質pass・固定ルールpromote・候補SHA一致を満たす比較は、最終判断inconclusive/rejectでも比較上の改善として扱うが、採用件数には加えない。これにより、sandboxで採用しない運用や人間判断待ちを性能停滞と混同しない。未計測とobserved-onlyは通常比較の連続・時間集計へ入れず、measurement_countsへ区別して残す。品質failed/unknownやsampleのpass=falseは合格にしない。観測用sampleの失敗・警告もquality_issuesへ残し、直近ならquality_evidenceで調査を促す。台帳の品質保留を解消する通知ではない。samplesがない旧記録はunknownとして保守的に数え、旧来の固定ルール採用だけは従来どおり連続を区切る。理由の文章から中止・sandbox等を推測しない。直近に閉じた実験が同じstable・同じhypothesisIdの再試行だった場合、同じ仮説の`strategy.parameters`がA→B→Aと往復した場合も通知する。時間は閉じた実験のstartedAt〜closedAtで、休止時間や工程別の損失を正確に表す指標ではない。LOOP_STARTED_ATより前の履歴は対象外。古い記録にパラメータがなければ往復は検知できない。JSON破損などの履歴不足はwarningで示す。

これらの件数は状況把握用で、採用率の分母やプラグインの時間短縮・得点への因果効果を定義しない。人間・依存・配布待ちも競技のwall clockを消費し、通知の計算から除外しても全体の時間予算は減り続ける。

これは停滞の原因を確定する判定でも、採用を止める追加ゲートでもない。閾値は`strategy.sh --window 4 --minutes 40 status`のように手動確認時に変えられる。通常のstatus/recordは既定値を使う。

通知、予測の外れ、重要な前提変更をきっかけに、安定状態で次を短く検討する。

1. 計測ノイズ・品質不足・復旧問題か、制約資源の見立てが違うかを分ける。
2. 現方針の継続、別の機構、構造変更、打ち切りの選択肢を挙げる。成立しない案を水増ししない。
3. 有力な説明を区別できる最小の観測・比較を選び、planの順序と反証条件を更新する。
4. 次のタスクを進める。再試行には新しい根拠を明記する。

毎タスクの追加会議・モデル呼出し・全員レビューは要求しない。計測不足の調査はAIが続け、人間には具体的な選択と比較結果・推奨を渡す。品質未確認を人間の承認で免除しない。

## 各セッションの探索を重ねる

各Discord主Agentは[PIPELINE](PIPELINE.md)に従い、候補準備と次候補調査を重ねる。
利用可能なnative SubAgentへ完了条件と時間上限を渡し、実装・関連QA・commit・READY
まで委譲できる。選手数をAgent数に読み替えず、小修正には不要な分担を増やさない。
調査・実装・検証のstage間を新たな指示待ちにせず、依存した実行順序は守る。

役割は固定しない。区切りでDiscordの最新方針・関連スレッドと`control.py queue`を読み、同じ原因への重複着手と、現stableで無効になった案を確認する。`--hypothesis`には共有の原因仮説キーを使い、同一キーの未完了タスクを重複作成しない。この照合は文字列一致であり、異なるキーの意味上の重複はAIが確認する。

READYが既定2件以上のとき、自動`task-claim`は調査・比較タスクへ向かう。タスクがなければ作成する。例えば、既存traceでlock待ちを反証する、候補の正しさをローカルで調べる、別機構の成立条件や現基準版への適用可否を比較する。実装を選ぶ理由がある場合は明示`--id`で取得できる。

新しい観測のために共有環境を変更したりベンチを回す必要があれば統合担当へ依頼する。読み取り調査タスクを名目に排他を回避しない。調査・比較の終了は担当者が`task-complete --reason '根拠artifactと結論'`で記録できる。コード採用には通常の統合・計測・採否が必要。

## 効果を確認する

これらの仕組みで得点が伸びるかは未検証。[比較手順](COMPARISON.md)で、最小構成と同じ条件・時間で比べる。悪化した場合は管理手順の時間、誤った優先順位、過剰な計測、探索の重複を調べ、効果のない手順を減らす。
