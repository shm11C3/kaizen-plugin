# 実験を選び、停滞時に方針を見直す

目的は制限時間内の最終有効スコア。実験数、commit数、AI稼働率だけでは成功としない。人間の戦略・除外事項・終了時刻を守り、通常の調査・実装・検証・採用は自走する。

## 次の実験を決める

統合担当が共有の`.kaizen/plan.md`を持ち、各メンバーはタスク・観測資料を入力する。`knowledge.sh plan`は候補と過去の結果を提示する。過去の採用率を今回の成功確率と解釈せず、次を揃えて順番を決める。

| 項目 | 記録すること |
|---|---|
| 採点とのつながり | 直接効く採点項目とマニュアル参照、または共有CPU・DB・lockなどを介する影響と観測根拠。不明なら短い調査を先に行う |
| 原因の説明 | 処理が重いのか、待ち時間なのか。どの資源が制約で、変更により何が解消するか |
| 効果と不確実性 | スコアへの期待効果と、その説明が成立する条件。局所的な速度改善だけで得点増加を断言しない |
| 総所要時間 | 実装、キュー待ち、配備、baseline更新、候補計測、復旧。残り時間と最終確認枠に収まるか |
| 前提と競合 | 必要な変更・現stable・触る資源・他候補との依存。採用後に前提が消えないか |
| 反証と打ち切り | どの観測で仮説を捨てるか、何回・何分で止めるか、別の説明と区別できるか |

`hypothesize`に固定の「index→N+1→cache」の順番はない。コーパスにない観測由来の案も追加する。基準版が変わったら保存された計画を読み直す。planの再生成は人間・AIの選択と独自の案を残すが、保存された判断が現在も正しいとは限らない。

複数の不可分な編集が一つの機構を実現する場合、組合せ候補として明示的に測る。前提変更だけのスコアが曖昧なら、その後の効果を推測して自動採用しない。大きな変更・リスク・トレードオフの人間判断は既存のPOLICYに従う。

## 停滞を検知したら

`status.sh`と`experiment.sh record`は履歴に基づくstrategy通知を出す。手動確認は`strategy.sh status`、検討テンプレートは`strategy.sh review`。チームでは統合担当が`control.py target ... strategy status` / `strategy review`を使う。

既定の通知条件は、固定ルールでの改善採用がない実験が3件続く、またはその実験内の経過時間が累計30分に達すること。直近に閉じた実験が同じstable・同じhypothesisIdの再試行だった場合、同じ仮説の`strategy.parameters`がA→B→Aと往復した場合も通知する。時間は閉じた実験のstartedAt〜closedAtで、休止時間や工程別の損失を正確に表す指標ではない。LOOP_STARTED_ATより前の履歴は対象外。古い記録にパラメータがなければ往復は検知できない。JSON破損などの履歴不足はwarningで示す。

これは停滞の原因を確定する判定でも、採用を止める追加ゲートでもない。閾値は`strategy.sh --window 4 --minutes 40 status`のように手動確認時に変えられる。通常のstatus/recordは既定値を使う。

通知、予測の外れ、重要な前提変更をきっかけに、安定状態で次を短く検討する。

1. 計測ノイズ・品質不足・復旧問題か、制約資源の見立てが違うかを分ける。
2. 現方針の継続、別の機構、構造変更、打ち切りの選択肢を挙げる。成立しない案を水増ししない。
3. 有力な説明を区別できる最小の観測・比較を選び、planの順序と反証条件を更新する。
4. 次のタスクを進める。再試行には新しい根拠を明記する。

毎タスクの追加会議・モデル呼出し・全員レビューは要求しない。計測不足の調査はAIが続け、人間には具体的な選択と比較結果・推奨を渡す。品質未確認を人間の承認で免除しない。

## 3セッションの探索を使う

役割は固定しない。区切りで`control.py queue`を読み、同じ原因への重複着手と、現stableで無効になった案を確認する。`--hypothesis`には共有の原因仮説キーを使い、同一キーの未完了タスクを重複作成しない。この照合は文字列一致であり、異なるキーの意味上の重複はAIが確認する。

READYが既定2件以上のとき、自動`task-claim`は調査・比較タスクへ向かう。タスクがなければ作成する。例えば、既存traceでlock待ちを反証する、候補の正しさをローカルで調べる、別機構の成立条件や現基準版への適用可否を比較する。実装を選ぶ理由がある場合は明示`--id`で取得できる。

新しい観測のために共有環境を変更したりベンチを回す必要があれば統合担当へ依頼する。読み取り調査タスクを名目に排他を回避しない。調査・比較の終了は担当者が`task-complete --reason '根拠artifactと結論'`で記録できる。コード採用には通常の統合・計測・採否が必要。

## 効果を確認する

これらの仕組みで得点が伸びるかは未検証。[比較手順](COMPARISON.md)で、最小構成と同じ条件・時間で比べる。悪化した場合は管理手順の時間、誤った優先順位、過剰な計測、探索の重複を調べ、効果のない手順を減らす。
